## 总则（一句话原则）

> **事实只由 L1 产生；诊断只由 L2 产生；预测只由 L3 产生；动作权限只在 L4 收口；
> L5 只执行已批准动作。执行结果只能作为新的 L1 事实回流。
> Web 不推断、不裁决、不直接执行，只承载展示与人工审批。**

这句话是本文档的最高条款。后续任何人提出"让 Council 顺便判断根因""前端按钮直接调
`pending_actions`""预测模型顺便修改板端告警阈值"之类的建议，均以此句作答：
**不属于这一层的权力。**

# WeakNet 网络体验评价体系

> 本文档是 WeakNet 评价模型的正式说明。阈值与判定逻辑**以代码为准**，文档描述当前实现状态；标注「待补」的部分属于后续增量。
>
> 最近更新：2026-09-12

## 一、这份文档要回答什么

WeakNet 的交付物不是一堆 eBPF 探针，而是一套评价体系。它要回答用户真正关心的三个问题：

> **现在网络能不能正常用？**
> **如果不能用，问题出在哪一层？**
> **系统有什么真实证据证明这个结论？**

反面例子：`网络质量：68 分`。这种输出既无法解释，也无法定位。

正面例子：

```text
Internet Access: BAD
Primary Issue: DNS resolution failure

Evidence:
  ✓ Wi-Fi link healthy
  ✓ IP gateway reachable
  ✓ RTT median 21 ms
  ✓ TCP retransmission 0.4%
  ✗ DNS transactions timed out (3 consecutive, no success interleaved)
  ✓ Observer healthy, no capture loss

Conclusion: 基础网络正常，当前故障位于 DNS 服务层。
```

## 二、模型结构

```text
                       Raw Evidence
    Ping / eBPF / nl80211 / Netlink / DNS
                              │
                              ▼
                    Evidence Capture
                              │
                              ▼
                【Evidence Quality】          ← 本增量新增的关键一层
                              │
                              ▼
                  Metrics / Transactions
                              │
             ┌────────────────┼────────────────┐
             ▼                ▼                ▼
      Core Network SLE   Service SLE      Advisory SLE
             │                │                │
      Reachability           DNS              RF Health
      Responsiveness     TCP Connect      共存干扰
      Reliability        HTTP Access
                           Captive Portal
             └────────────────┼────────────────┘
                              ▼
                   OverallPolicy(profile)
                              │
                  Coverage / Applicability
                              ▼
                     StateStabilizer
                              ▼
       ┌──────────────────────┼──────────────────────┐
       ▼                      ▼                      ▼
  Overall State         Primary Issue          Evidence
  BAD/DEGRADED/GOOD     根因定位               证据链
       │
       ▼
  display_score / legacy 0~4   （仅兼容投影）
```

**核心转变**：不再有公式把 RTT、RSSI、丢包、DNS 加权混成一个总分——那样一个维度的好会掩盖另一个维度的严重故障。状态与证据是内部真值。

## 三、问题一：BSSID 空间图

### 输入

第 3 项已在遥测快照里上行 `ap_bssid` / `ap_ssid` / `link_type`（含精确频段）。
每台网关各自知道自己关联的是哪个 AP。

### 关键洞察

同一车间里，多台网关**听到同一个 AP 的 BSSID** 是常态（AP 覆盖重叠）。
BSSID 是 IEEE 分配、全球唯一且**不随机化**的（与设备 MAC 不同），因此它是
唯一可靠的"固定锚点"。

### 由此可以做什么

- **锚点图**：把 `BSSID → {gateway_id, RSSI, 时间}` 聚合成"哪几台网关能听到哪个 AP"；
  这给出了**网关之间的相对位置约束**（能同时听到同一 AP 的网关必然地理接近）。
- **环境证据**：AP 数量与信道分布在 site 内是稳定事实，可作为区域级环境基线。

### 1.3 A76 大核纯 CPU 推理的性能预估

| 阶段 | 计算量 | 预估耗时 | 说明 |
|------|--------|---------|------|
| Prompt 处理 (500 tokens) | O(n²) attention | ~8-15 秒 | 首 token 延迟 (TTFT) |
| Token 生成 (每 token) | O(n) 自回归 | 55-100ms/tok | 即 10-18 tok/s |

### 部署阶段会做什么（2026-11-01 加固）

跑 `ci.sh` 时如果发现下面这些行为，都是**设计如此**，不是异常：

| 行为 | 原因 |
|------|------|
| 先 `rm -rf .deploy-staging` | 该目录是纯中转区，历史 root 属主日志会让 `rsync --delete` 恒失败（Permission denied / code 23）。每次部署前整体清空。 |
| 暂停 `weaknet-ota-recover` | 它是常驻轮询，看到 `TRIAL` + 健康就自动 commit，会与 adopt 抢同一 OTA 事务，导致 adopt 的 commit 被判"非法阶段转换"。部署期间由 `ci.sh` 独占事务，结束（含失败/Ctrl-C）自动拉起。 |
| 反向隧道重启后报 `Connection ... closed by remote host` | 重启隧道必然掐断承载该命令的通道（自指）。**不是失败**。`ci.sh` 随后轮询等待通道真正恢复（判据是完整 SSH 握手，不是端口 listen），实测 5～50s。 |
| adopt 返回非零但仍继续 | 会先用 `phase=COMMITTED` + `.committed` 存在 + 服务 active 三条客观事实复核；全部满足则判定为成功（避免跳过后续步骤的"假失败"）。 |

## 改进点1：planning_fingerprint 哈希范围过大

### 问题

`planning_fingerprint` 对整个 `design.md` 文件做哈希。修改 `design.md` 的任何字段（如 Implementation Economy 分类配置、Integration Completeness 块），都会导致 `planning_fingerprint` 变化，使所有已记录的 TDD 证据失效（因为证据绑定了 `planning_fingerprint`）。

**实际影响**：改一个分类字段导致 10 个任务的 TDD 证据全部作废，需要重跑全部 RED→GREEN→REGRESSION。

### 修复

修改 `scripts/manifest_policy.js` 的 `planningStateAt` 函数：对 `design.md` 只哈希 TDD Policy 块（`<!-- autoai:tdd-policy:v1 -->` 之间的内容），不哈希整个文件。

修复后：
- 改 Implementation Economy 分类 → `planning_fingerprint` 不变 → TDD 证据不失效 ✅
- 改 Integration Completeness → `planning_fingerprint` 不变，`integration_completeness_sha256` 变化 → 只影响集成验收，不影响 TDD 证据 ✅
- 改 TDD Policy → `planning_fingerprint` 变化 → TDD 证据失效（正确行为）✅

### 修改文件

- `scripts/manifest_policy.js`（`planningStateAt` 函数的 `add` 回调）
- `.ai-harness/manifest.json`（同步更新 content_sha256）

## 1. 架构总览

WeakNet 的 OTA 升级采用轻量级软件双槽位（Slot）设计，避免在嵌入式系统上对 Flash 重新分区的巨大风险。

```text
开发板 /home/radxa/weaknet/
├── releases/                     # 多版本隔离目录
│   ├── legacy-flat/              # 首次部署自动归档的旧扁平布局
│   ├── 1.0.0/                    # 历史稳定版（保留供回滚）
│   └── 1.1.0/                    # 当前激活版本
│       ├── server/               # 服务端二进制与 eBPF 对象 (*.bpf.o)
│       ├── client/               # 客户端工具 (weaknet-cli 等)
│       ├── lib/                  # 运行时动态库 (libbpf.so 等)
│       ├── VERSION               # 本版本号 (1.1.0)
│       ├── manifest.sha256       # 全量文件 SHA256 校验清单
│       └── .committed            # 健康窗口通过后的“转正标记”
├── current -> releases/1.1.0     # 【原子翻转点】基于 Linux rename 原语切换
├── server -> current/server      # 兼容软链，历史命令与路径 100% 保持有效
├── client -> current/client
├── lib -> current/lib
├── weaknet-local-update.sh       # 本地升级执行体（随包下发并自动自更新）
├── data/                         # 【绝对只读隔离】5 个核心状态文件（history.db、epoch 等）升级永不触碰
└── config/                       # 【绝对只读隔离】release_pub.pem 与 config.yaml

系统路径（不随 OTA 制品变化）：
├── /usr/local/lib/weaknet/weaknet-ota-ctl   # 升级事务控制器（P0-A，唯一的指针/状态写入口）
└── /var/lib/weaknet-ota/transaction.json    # 事务状态（schema v1，root 独占 0600）
```

### 1.1 为什么需要事务控制器（P0-A）

**升级机制的可靠性不能完全依赖被升级的 weaknet-server 本身。**

原实现里 `current` 指针、`.previous` 回滚指针、`.committed` 转正标记由
`cmd_apply` / `cmd_rollback` / `cmd_adopt` / legacy 迁移 / `--commit` 多条
执行路径各自读写。一旦升级进程在关键窗口被掉电或杀死，**没有任何一方知道
这次升级做到哪一步**：指针翻了但没转正，还是转正了但投影没写？无从判断。

P0-A 把三件事收口到一处：

| 收口项 | 权威位置 |

# 网关动作目录版本契约（跨端执行前置条件）

> 状态：2026-10-08 实施中
> 关联：路线图 ⑤（Action Policy）的 fail-closed 防线；⑥ 的真机排练复核

## 一、问题（为什么需要这份契约）

路线图 ⑤ 的 Policy 有一条 fail-closed 防线：

```text
云端审阅目录 != 目标网关宣称目录 → allowed=False（catalog_version_mismatch）
```

`action_policy.py:202` 实现正确、单测覆盖充分（`test_action_policy.py:118` 等
`gateway_catalog_version="cat-old"`）。**但真实运行中这条防线永不触发**：

- `build_request_from_tables()` 从不设置 `gateway_catalog_version`，恒取默认值
  `TOP_LEVEL_CATALOG_VERSION`（`network_council_service.py:150`）；
- 板端从不上报任何目录版本（上行报文只有 `schema_version`）；
- 全仓所有非默认值 **100% 出现在 `tests/` 里**。

结论：这不是"缺陷"，是**未接线**——云端与网关各自持有目录，但**没有任何一侧
对比过**。本契约把这条比较接上，让 ⑤ 已有的防线真正具备输入源。

## 二、契约

### 2.1 指纹算法（两端必须逐位一致，否则真机全量误判漂移）

指纹 = SHA-256（12 位十六进制前缀），输入是**规范 JSON**：

```json
{"actions":{"<action_id>":{"params":[{"allowed":[...],"name":..,"required":..,"type":..}]}},
 "config_keys":["<key>",...]}
```

规范化要求（与云端 `_canonical_payload()` 完全一致）：
- 顶层键顺序固定：`actions` 在前、`config_keys` 在后；
- `actions` 的键**按 action_id 升序**；
- 每个 action 只有一个 `params` 键；param 字段顺序固定为
  `allowed, name, required, type`；
- `config_keys` **按字典序升序**；
- 无空白（separators `("," ":")`）。

`allowed` 为空时须序列化为空数组——两端必须**同样输出** `"allowed":[]`。

金标向量（两端必须都得到此值）：

```text
bdb093ac5310
```

### 2.2 传输

| 项 | 决定 |
|---|---|
| 通道 | 复用既有 `/api/v1/network/edge/wireless-events`（**不新增端点**） |
| 字段 | 顶层 `catalog_version: str \| None`，可选，1–64 字符 |
| 语义 | 设备**自述**其 L5 可执行目录指纹；服务端只做事实记录与对比，不据此授权 |

### 2.3 缺失语义（关键：决定会不会把现有真机全线阻断）

| 情形 | 行为 | 理由 |
|---|---|---|
| 设备上报版本 == 云端 | 记录；Policy 放行 | 正常 |
| 设备上报版本 != 云端 | 记录为漂移事实；Policy 依 ⑤ 原语义 fail-closed | 本契约要接通的正是这条 |
| 设备**未上报**（`None`） | **不阻断**：回落既有"无漂移事实"语义 | 缺数据不等于漂移。若把缺失当漂移，所有旧固件与排练环境会被全线 403，而它们并没有被证明跑在漂移目录上 |

「缺失 = 不阻断」是**刻意的保守选择**：本契约的目标是让"已声称的漂移"可被发现并
拒绝，而不是把未�
