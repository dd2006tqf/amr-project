# 失败规避守则（提炼自 2026-11-02 实战）

> 这是 `TOOL-RELIABILITY.md` 的补充篇，专门针对**输出截断**和 **DSML 泄漏**两类问题。
> 每次会话开始前应当先读这两份文件。

---

## 第 2 类 · 输出截断（可以大幅降低）

### 现象

Write 工具输出长内容时**静默截断**，不报错，文件末尾可能停在半句或出现字面量 `…`。

### 实测记录

- 写 258 行 Python 代理脚本，连续被截断 **3 次**
- 写 Windows 安装脚本，尾部停在 `# UTF-8 无 BOM 写入，避…`
- 写 SSE 分析器，第一次没落盘，第二次才成功

### 对策

| 措施 | 说明 |
|---|---|
| 单次写入 ≤ 约 100 行 | 超过就分块 |
| 分块追加，不一口气写完 | 用 `>>` 追加，逐块验证 |
| 写完立刻四项自检 | 见下 |

四项自检（缺一不可）：

```bash
python3 -m py_compile <file>    # 1. 语法（按语言替换检查器）
wc -l <file>                     # 2. 行数符合预期
tail -3 <file>                   # 3. 尾部是完整语句
grep -c '…' <file>               # 4. 截断特征应为 0
```

**注意**：工具回显本身也会截断。判断文件是否完整，只看磁盘真实内容，不看工具输出末尾。

## 第 3 类 · DSML 泄漏（无法根治，只能降低概率）

### 现象

输出末尾混入 DeepSeek 原生工具调用分隔符，例如：

```
<｜｜DSML｜｜parameter>
</｜｜DSML｜｜invoke>
</｜｜DSML｜｜calls>
```

也可能出现非标准 `<tool_call>` 标签、管道符乱码、内容重复输出。

### 根因（已确认为上游，非本机可修）

中转站 `laneai.dev` 需要把 DeepSeek 原生工具调用协议实时翻译成 Anthropic 的 SSE 事件流。
转换层在中途发生错位时，会把原生分隔符当作普通文本透传出去。

**关键证据**：本地代理只改 `usage.input_tokens`，正文一个字节都不碰。泄漏在转换前就发生了，
位置在中转站的协议转换层，代理接触不到。

### 触发因素（观察所得）

| 触发因素 | 说明 |
|---|---|
| 工具调用参数结构复杂 | 参数里嵌 heredoc、多层引号或含大量转义的 JSON 时，转换层容易在中途发生错位 |
| 连续调用工具 | 在同一个回合里密集调用工具时更容易发生 |
| 上下文较长 | 上下文越长，转换层处理每块的负担越大 |

### AI 侧可做的

- 工具调用参数尽量简单，避免在 JSON 里嵌 `<<'EOF'`
- 写文件时改用分块写入，不用大 heredoc
- 一次只做一件事，不做连环调用
- 第一次失败就告诉用户"这条调用被污染了，我换个方式重试"，不要默默重试

### 用户侧可做的

1. **调低压缩窗口**。`CLAUDE_CODE_AUTO_COMPACT_WINDOW` 从 200000 降到 150000，
   压缩更早触发，上下文余量更大。代价是压缩更频繁（每次约 40 秒）。
2. **会话出问题就重启**。连续两三次输出异常，这个会话状态大概率已经坏了，
   开新会话比硬撑省时间。
3. **不重要的会话别开太长**。长会话让泄漏概率单调上升。

---

## 最重要的一条行为准则

**遇到工具失败，第一次就向用户说明，不要原地反复重试。**

用户发"？"和"继续呀"的那几次，本质上都是我在异常面前没有及时汇报。
正确的做法是：第一次失败就说明情况，而不是默默重试到用户觉得不对劲。
